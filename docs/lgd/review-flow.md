# レビュー対応のフロー

作成: 2026-11-24。PR にレビューが来たときの対応手順と、PR #22 のレビュー（2026-11-24「データ基盤・後続ウィジェット実装者レビュー」、対象 head `0237f82`）への対応方針をまとめる。

## 1. 手順（毎回）

1. **集める**: PR の review / review comment / issue comment を取得し、1つの指摘を1行にした対応表（下の 3章の形）を作る。ボットのコメント（デプロイ通知など）は対象外。
2. **分ける**: 各指摘を、正本（仕様書・実装ガイド・部品シート）に照らして次のどれかに分ける。
   - **修正する**: 正本どおりでない、またはデータを失う・壊す可能性がある。
   - **資料で明確にする**: 実装は正しいが、決めごとが資料から読めない。
   - **後の段階で行う**: 正本で P3/P4 や未決定（実装ガイド 7.6）とされているもの。理由と段階を書く。
   - **判断を仰ぐ**: 正本にも合意にも答えが無く、利用者の判断が要るもの。
3. **受け入れ条件をテストにする**: レビューの AC を、修正の前に単体テスト・fixture・e2e の形で書く（失敗することを確かめてから直す）。見た目に関わるものは再現度テストのシナリオも確かめる。
4. **層に割り振る**: [開発フロー](./development-flow.md) 3章の4層に割り振る。同じファイル群に触る指摘は1つの担当にまとめ、並行作業で触る場所が重ならないようにする。データの形（ID・版・保存）を変える指摘を先に片付け、それに乗るもの（Undo、登録項目、通信）を後にする。
5. **直す**: 指摘ごと、または関係する指摘のまとまりごとに1コミット。コミットメッセージに指摘番号を書く（例 `fix(lgd): review#1 …`）。
6. **ゲートを通す**: `npm run check`、`npm run build`、`npm run build-storybook`、e2e、再現度テスト（48 画面）。加えて、データに触れた指摘は**機能・データのゲート**（往復・負 fixture・保存 bytes の維持）を通す。数値の再現度だけで合格にしない。
7. **記録して返す**: この文書の対応表に、状態・コミット・テストを書く。PR にはレビューへの返信として、項目ごとの対応・コミット・確認結果・残した範囲を1つのコメントで返す。マージや承認の操作はしない。
8. **次の段階へ**: 「後の段階で行う」にしたものは、その段階の開始条件として [開発フロー](./development-flow.md) に書き写す。

修正は同じ PR に積む（ユーザー決定 2026-11-24）。P2 以降は分類ごとに別 PR にし、このブランチに積み重ねる（ベースを前の PR のブランチにする）。

## 2. PR #22 レビュー（2026-11-24）への対応方針

前提（レビュー 0 章、再設計しない）: ボードと画面は別、全画面はサイズの選択肢、`pg`/`multi` は種類ごと、置いた1個の ID（`links#2`）が設定と記録を持つ、共通の元に戻すの範囲は仕様書 7 章のとおり、区画ごとの版、v0 からの移行はしない、P2/P3/P4 の分け方は維持。

| # | 指摘 | 分類 | 方針（決めたこと） | 担当 |
| --- | --- | --- | --- | --- |
| 1 | 版の管理と、import の破壊的なフォールバック | 修正 | 全体の区画に `v`、ウィジェットの区画に `v`（区画の形の版）と `dv`（記録の版 = `WidgetDataDef.version`）を持つ。**未来の版・不正な区画は読み込まず、保存 bytes にも書かない**（その区画は読み取り専用として残す）。古い版は `migrate` があれば移し、無ければ未来版と同じく残す。import は封筒の `format`/`v` と各区画の版を**反映前にすべて検証**し、1つでも対応外があれば何も変えずに失敗を知らせる | データ層（UI/UX 実装層） |
| 2 | 区画保存なのに最初の変更で他の区画も上書きする | 修正 | 起動時の読み込み結果を区画ごとの基準にし、**変わった区画だけ書く**。2つの Dashboard が同じ保存先を使うテストで、別の区画の変更が互いを消さないことを確かめる。同じ区画を2つのタブで同時に変えたときの扱い（後勝ち）は P3 のタブ同期まで未対応と明記 | データ層 |
| 2a | （関連）storage イベント | 後の段階 | 他のタブの変更を反映する処理は P3（実装ガイド 7.3）。それまでは「別の区画を消さない」ことだけ保証する | — |
| 3 | 読み込みの元に戻す、メモからの追加の元に戻す | 修正 | 共通の履歴の範囲は広げない。読み込みは**反映前の全区画の写し**を持ち、トーストの「元に戻す」でそれを戻す。メモからの追加は**追加した行の ID だけ**を消す（ほかの編集は残す）。上限で古い行が落ちた場合は、その行も戻す | ウィジェット層＋データ層 |
| 4 | 固有設定・参照の検証、書き出しの結果 | 修正 | `st`/`rg` の min・max・step、`tm`（HH:MM）、`dt`（YYYY-MM-DD）、`tx` の長さ、全体設定の数値（不正な値は既定値）、ボード ID とウィジェット ID の重複・参照切れを検証する。同じ検証を UI・復元・import で使う。外部入力の検証は Zod（既存の方針）に寄せ、検証の定義は1か所にする。クリップボードへの書き出しは**書けたことを確かめてから**「コピーしました」と最後の書き出し日を更新し、失敗なら知らせて日付を変えない。ファイル保存は、保存先を選べる API（`showSaveFilePicker`）があれば完了を待ってから、無い環境では「ファイルの保存を始めました」とし、完了とは言わない | データ層 |
| 5 | `multi` / `pg` と区画 ID の契約 | 修正 | **種類 ID（登録のキー）と配置 ID を分ける。** 配置 ID は最初の1個が種類 ID そのもの（`links`、既存7個の ID と見た目は変えない）、2個目以降は `links#2`。`order`・`place`・`sizes`・`off`・`pins`・`lockSz`・`pgW` と区画 `w:<配置ID>` は配置 ID で持つ。部品は配置 ID を受け取り、`useWidget()` で自分の設定・記録を読む。全画面は「`pg` の種類で `pgW[配置ID]` が真の配置」を汎用に扱い、時計・スケッチ専用の分岐（`FULL_SCREEN_IDS` など）をなくす。`multi:false` の種類は2個目を作れない（関数で拒否し、テストする）。複数置く UI と記録の共有の選択は P3、共有の対象（`share`）は未決定のまま既定は独立 | データ層 |
| 6 | 登録表の残り項目と共通枠の責務、プライバシー | 修正 | 登録に `priv`（仕様書 3 章の既定オンのリスト。`vd` と独立）、`states`、`refresh`、`keys`、`store`（`WIDGET_DATA` から引く。二重管理しない）を足す。`icon` と `share` は値が決まるまで未定義を許す。共通枠は登録の `net`/`perm`/`states` から接続の点・状態の覆い・1×1 の知らせを出す（各ウィジェットで手で指定しない）。**人前では隠すを最優先**にし、状態の覆い・1×1 の知らせ・全画面・前面表示でも中身と読み上げを出さない。プロトタイプの CSS の打ち消しは別ファイル（`src/app/styles/overrides.css`）で直し、`dashboard.css` は変えない | UI/UX 層＋ウィジェット層 |
| 7 | 重い記録・実行・通信の差し替え | 修正（境界だけ） | 大きな記録のための**非同期の記録の保存先**（IndexedDB、Dexie）を最小限作り、P2 で大きな記録を持つ分類（受け渡し・AIチャット・表・スクリプト・録音・画像変換）はそれを使う。保存しないもの（録音、画像変換の画像、現在地、スクリプトの結果、会話保存オフの会話）を記録の定義とテストに写す。天気の段の取得は**表示中の画面のときだけ**行い、表示されていない段・画面では更新しない。重いウィジェットは表示されるまで描画しない仕組みを用意する（今の7個の見た目は変えない） | データ層＋ウィジェット層 |
| 8 | 正本・既存の契約・手順の整合 | 資料で明確にする | `widget-schema-v0.md` の旧規約を維持する一文と R3・R9 を直す。`tool-module-contract-v2.md` と `quality-gates-v2.md` に、ブラウザの画面とデータは lgd の資料が正本で、旧 placement/instance/standalone/削除の三択/IDB revision は MCP・remote の将来契約にだけ適用する、と書く。V01–V15 を「現行要件/廃止/P3/P4/テスト」に対応づける。`lgd-add-widget` スキルに登録項目・ID・版・プライバシー・状態・個別の元に戻す・見本と実機能の区別を入れる。開発フローに**機能・データのゲート**を足す | 資料 |
| 9 | 未実装・見本・実際の機能の区別 | 修正 | 一覧は46種のまま見せる。未実装の種類は、置く・置かずに使うと**中身の置き換え（印・見出し・説明）で「準備中」**を出し、空白にしない。追加の操作は成功扱いにしない（「準備中です」と知らせて置かない）。見本のデータで動くもの（天気・傘など）は接続の点で見本であることを示す（既存）。人間確認と公開の条件（未実装が残っていないこと、プロトタイプ専用の機能が本番に出ないこと）を開発フローに書く | UI/UX 層 |
