## 1. 目的・対象・現在地

**目的:** 新しい Claude Design の画面を、共通設定と Parts / Shell / controller / 保存の責務へ無理なく対応付ける。画面に必要なものを見て v0 を調整し、その後の実装単位・受け入れ条件を決める。

**今回の対象:** ウィジェット種別、共通操作、部品構成、サイズ別表示、通信状態、通知・スクリプトの境界、ファイルの役割、実装前の確認条件。

**対象外:** プロダクトコードの追加、DB 移行、フレームワーク変更、API 契約・課金、スクリプト実行基盤の選定、第三者プラグイン、デプロイ。既存 [#16](https://github.com/clockcrockwork/Tool-Dashboard/issues/16) / [#18](https://github.com/clockcrockwork/Tool-Dashboard/issues/18) を重複して立て直さない。Vue 3 + Vite + TypeScript は確定済み。比較 [#17](https://github.com/clockcrockwork/Tool-Dashboard/issues/17) は not planned で終了しており、待ち条件へ戻さない。

| 確度 | 内容 |
| --- | --- |
| 会話で確認済み | ページ／ツール／両対応、サイズ変更、位置・サイズ固定、表示、部品構成、サイズ別内容、接続先、オフライン・空・エラー、通知・処理を設計へ含める |
| repo で確認済み | 四層契約、配置と設定の分離、現行コードの限られた配置・画面・型。確認 commit は設計案冒頭 |
| 今回の設計案 | ページ本文の単一配置、独立ロック、構成参照、状態の独立した軸、view の寿命。コードへまだ接続していない |
| 仮置き | 例示の CSS px 閾値、天気の15分鮮度・セッションキャッシュ、ページ本文という解釈 |
| 未確認 | 新しい HTML、実画面の制約、実操作、API、sandbox 性能・安全性、実機表示 |

## 2. 設計資料としての受け入れ条件

これは**設計 PR の完了条件**。次節の UI・runtime 条件と分ける。

- [ ] 既存正本と現在のソースを読んで、実装済み／提案／仮定を区別している。
- [ ] kind / placementId / instanceId / viewId / targetRef と設定の所有者を混同していない。
- [ ] ユーザーが挙げた要件を、所有者・宣言する場所・確認条件へ対応付けている。
- [ ] 時計・天気・スクリプトの三例が同じ責務と部品体系で記述できる。
- [ ] JSON 例は構文が正しく、部品参照・required・バリアント既定・サイズの整合を確認している。
- [ ] 文書リンク、Markdown の構造、差分の空白、変更対象が文書のみであることを確認している。
- [ ] 独立レビューで既存契約との衝突・実装計画を妨げる不足を確認し、対応結果を記録している。

チェック結果は PR に実際の証拠を記録する。このページを置いたこと自体で自動的に完了にはしない。

## 3. 新しいプロトタイプ／実装の受け入れ条件

下表は **すべて未検証**。HTML を読むだけで処理・保存・実機動作の PASS にしない。「prototype」は視覚・操作の検証、「implementation」は本番コードでの検証を指す。

| ID | 観点と試し方 | 期待する結果 | 必要な証拠 |
| --- | --- | --- | --- |
| V01 | tool-only / page-only / 両対応を登録し、配置候補とページ単一枠を選ぶ | 未対応の表示は選べない。single は最大一件で、未配置は null を明示。直接 standalone と既存 instance の拡大を区別 | prototype の導線＋implementation の参照検証 |
| V02 | 同じ kind を別設定で二つ配置し、同一 instance を参照する別 view も開く | 別設定は独立。共有設定でも draft は独立し、競合時に上書きしない | implementation の保存・view・競合確認 |
| V03 | 位置固定のみ、サイズ固定のみ、両固定、リサイズ非対応を試す | 操作の許可が独立。位置固定時のサイズ変更で基準位置を動かさない | prototype の操作と無効状態＋implementation |
| V04 | 隣接する配置を移動・自動整列し、画面幅も変える | 固定配置の保存位置・サイズを巻き添え変更しない。狭い画面でも操作可能 | implementation の layout 差分＋表示確認 |
| V05 | ボード／single の配置を非表示→再表示 | 参照・設定・データを保持し、管理導線で戻せる。削除と混同しない | prototype＋保存の前後比較 |
| V06 | 各例を小・大・境界寸法・高さ不足で表示 | 最初の一致／既定が決定的。内容領域の寸法で切替。必須操作へ到達可能 | prototype、将来の Storybook、keyboard/touch |
| V07 | 不完全な入力、dirty draft、実行中にサイズ・テーマ・テンプレートを変える | 入力と実行 ID を維持、再実行なし、フォーカスを適切に引き継ぐ | prototype の入力操作＋implementation の実行回数 |
| V08 | 天気 W1〜W8 と、初回失敗・不正応答・未取得 offline を試す | empty と失敗を区別。stale＋更新失敗＋offline を併記し、更新成功で解消 | prototype の状態切替＋adapter/controller fixture |
| V09 | 天気の地域・単位を変更し、旧要求を遅く完了させる。同一 key の競合・認証sourceの権限失効も試す | 新しい対象や共有キャッシュを旧値で上書きしない。失効時は表示を止め、古い応答を再格納しない | implementation の要求・認可世代とキャッシュ確認 |
| V10 | ページ切替／非表示／再表示を繰り返す。dirty・実行中も含める | 無断で入力を捨てず、破棄時に専有資源を解放。共有購読は他 view を維持 | prototype の離脱導線＋implementation の解放確認 |
| V11 | 一つの更新失敗を何度も再描画し、複数 view で同じ更新を受ける | feedback は維持、通知は重複しない。再読込みイベントで書込みを起動しない | implementation のイベント数・意図確認 |
| V12 | script の Run→Stop→再実行と古い応答を試す | 停止を確認してから停止済み表示。古い結果の上書き・import時の自動実行なし | prototype UI、実行自体は #16 の検証 |
| V13 | 旧配置を復元し、新しい lock / visible を含めて export→import。未知版も投入 | 版・移行が明示され、未知データを原文保持。revision と削除の三択を維持 | implementation の移行・往復・失敗 fixture |
| V14 | compact / page、ライト／ダーク、keyboard、touch、reduced motion | 必須 feedback / Stop / 確認を隠さず、focus・可読性を確保 | Storybook/Playwright と、Windows Chrome / 実機 iPhone Safari の結果を別記 |
| V15 | single の最後の配置を三択で削除・別ページへ移動し、export→import。処理中の競合・失敗も試す | ページを保持し、成功時だけ参照を null にする。所属変更はローカルで一体保存し、失敗時に参照切れを作らない。未知の参照切れ import は保全 | prototype の空ページ＋implementation の transaction・revision・往復確認 |

将来のブラウザ実行は、シミュレートした WebKit と実機 Safari を区別して記録する。実行基盤未実装の stub では V12 の UI 部分だけを確認できる。offline 表示が成功しても、オフライン初回起動や権限隔離を証明したことにはならない。

## 4. HTML が共有されたら行う手順

1. 提供された版とファイルを固定し、現行 repo / AGENTS.md / CLAUDE.md / 関連 PR を再確認する。2025年の prototype.jsx へ読み替えない。
2. 各画面を **Shell / ツール内容 / 設定 / 状態表示 / 操作** に分類する。個別 DOM をすべて新しい Part にする必要はない。
3. ページ単一とボード配置の意味、配置単位、サイズ別の必須内容を V01 / V03 / V06 で照合する。
4. 時計・天気・スクリプトに例を当て、V05 / V07 / V08 / V10 / V12 の不足状態を一覧にする。HTML にある表示と、まだ必要な表示を区別する。
5. 差分を「共通スキーマ」「ツール固有」「ホスト」「#16・#18 の別課題」へ振り分け、v0 の最小修正と実装 AC に変換する。

Claude Design には構成・状態・操作だけを渡す。API・Worker・DB・フレームワークの実装を要求せず、Design Pattern Gallery に状態を整理する。Storybook は実コンポーネントを作る工程で設ける。

## 5. 実装前の優先順位・判断を戻す条件

優先順は **新 HTML との照合 → 共通表示・配置契約の最小修正 → 最初の実装単位と移行条件の確定**。その後に既存の品質ゲートでコードを進める。現行コードにない全フィールドを一括実装する計画にはしない。

次の場合は既存の確定仕様を勝手に変更しない。

- 「ページ」が複数ツールを合成する別種の画面だった場合や、利用者が任意の部品・処理を組み立てる編集機能を必要とする場合。
- 表示変更のために配置・設定の所有者、削除の三択、未知データの保全を変えなければならない場合。
- 非表示中・アプリ終了後のスクリプト継続、Push、常時通信、永続キャッシュが必要になり、実行寿命・保存範囲が変わる場合。
- フレームワーク移行、未選定 API の課金／認証、remote access、MCP 公開範囲を新たに決める必要がある場合。

通常の閾値・余白・命名など、確定要件を変えない調整は根拠を記録して進めてよい。
